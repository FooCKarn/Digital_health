# สเปก: ผู้ช่วยแชต "ถามต่อจากผลตรวจ" (RAG แบบคุมได้)

สถานะ: ร่างรอทีมรีวิว (2026-10-06) · ผู้ตัดสินใจ: ทีม (เลือกที่เก็บประวัติแบบ sessionStorage, เฉพาะแผงแชตก่อน, เอาตัวตรวจอาการฉุกเฉิน, อนุญาตแก้กฎข้อ 4 แล้ว)

## 1. เป้าหมาย และสิ่งที่ผู้ใช้ได้
ผู้ใช้ที่ได้ผลตรวจแล้วถามต่อได้ในแผงแชต เช่น "ทำไมขิงห้ามกับ warfarin", "รางจืดใช้ได้กี่วัน", "ควรถามเภสัชกรว่าอะไร" แล้วได้คำตอบที่ **ผูกกับข้อมูลในหนังสือ** พร้อมเลขหน้าและวลีหลักฐาน ไม่ใช่คำตอบจากความจำของโมเดล

ความสำเร็จวัดได้: (1) ชุดคำถามทดสอบ `docs/rag_eval.json` ค้นรายการที่ถูกต้องเจอตามเกณฑ์ที่ตั้งไว้ และปฏิเสธคำถามที่ไม่ควรตอบได้ถูกต้องทุกข้อ (2) ไม่มีสิ่งแปลกปลอม/คำปลอบใจ/ข้อมูลนอกรายการหลุดถึงผู้ใช้ในเทสต์ที่จำลอง LLM แบบประสงค์ร้าย (3) ใช้งานได้เต็มโดยไม่มี LLM (ตอบจากฐานข้อมูล)

## 2. ไม่ทำในสเปกนี้ (YAGNI)
แชตเปิดกว้างที่ AI ตอบอะไรก็ได้; ประวัติฝั่งเซิร์ฟเวอร์; ส่งประวัติแชตให้ LLM; embedding/vector DB; streaming; เสียง; อัปโหลดไฟล์/รูป; รีสกินทั้งเว็บ (งานแยก); ขนาดยา การวินิจฉัย การแนะนำตำรับ

## 3. หลักการที่ห้ามละเมิด (อ้าง CLAUDE.md)
- กฎข้อ 1/3: ข้อเท็จจริงทุกข้อในคำตอบมาจากรายการที่ค้นได้ ไม่เพิ่มเอง
- กฎข้อ 4 (c): LLM เรียบเรียงจากข้อความที่ค้นได้เท่านั้น อ้างรหัสรายการ ผ่านตัวตรวจ ไม่ผ่านใช้ข้อความฐานข้อมูล **ไม่ส่งประวัติแชตให้ LLM**
- กฎข้อ 5: ห้ามตอบว่า "ปลอดภัย/ใช้ได้" แทนการไม่พบธง; ขอบเขตและ "ไม่ใช่การวินิจฉัย" แสดงถาวรในแผงแชต
- กฎข้อ 7: รายการคำ/เกณฑ์ที่ทีมตั้งเองอยู่ใน `data/config.json` พร้อมป้าย "ทีมตั้งเอง" ห้ามฝังในโค้ด
- กฎข้อ 9: แสดงเฉพาะวลีสั้นหลักฐาน (≤ 250 ตัวอักษร ตามเทสต์ที่มีอยู่) ไม่คัดลอกข้อความยาว
- กฎข้อ 10: ข้อมูลสมมติเท่านั้น; ช่องแชตมีคำเตือนห้ามพิมพ์ข้อมูลส่วนตัว

## 4. สถาปัตยกรรมและการไหลของข้อมูล

```
เบราว์เซอร์: ปุ่มแชตลอย -> แผงแชต (ประวัติใน sessionStorage)
   POST /api/ask {herbs, drugs, profile, question, context_herbs[]}   (ไม่ส่งประวัติแชต)
      -> engine/service.py ask(): validate -> check() คำนวณผลตรวจใหม่ (ไม่เชื่อค่าจากเบราว์เซอร์)
      -> engine/rag.py:
           1) intent (กฎตายตัว): emergency | safety_yesno | dose | diagnosis | lookup
           2) emergency -> ข้อความฉุกเฉินตายตัว (ไม่เรียก LLM ไม่ค้น)
           3) safety_yesno -> ข้อความตายตัวจากผลตรวจ (ธงที่พบ หรือ "ไม่พบธง... ไม่ได้แปลว่าปลอดภัย")
           4) dose/diagnosis -> ปฏิเสธตายตัว + แนะนำเภสัชกร
           5) lookup -> retrieve(top-k<=4, ขอบเขต: สมุนไพรในผลตรวจ + ที่ถูกเอ่ยชื่อ + context_herbs)
                 คะแนนต่ำกว่าเกณฑ์ -> ปฏิเสธตายตัว "ไม่พบข้อมูลในฐานข้อมูลนี้"
                 ไม่งั้น -> คำตอบแบบสกัดข้อความ (ค่าเริ่มต้น)
                          -> ถ้ามี LLM: เรียบเรียงจากรายการที่ค้นได้ -> validate -> ผ่านใช้ / ตกกลับแบบสกัด
   <- {source: database|llm|refusal|emergency, text_th, cites[], follow_ups[], rejected_reason?}
```
เซิร์ฟเวอร์ไม่เก็บอะไรและไม่บันทึกเนื้อหาคำถาม (ไม่มี `print` ของคำถาม)

## 5. คลังข้อความ (corpus) และการค้น
- **หน่วยค้น:** ทุกรายการใน `data/herbs.json` (ข้อห้าม คำเตือน ยา ระยะเวลา ข้อควรระวัง) 108 รายการ รหัสคงที่ `{herb_id}.{kind}.{n}` ข้อความของหน่วย = ชื่อสมุนไพร + `text` + ป้ายเงื่อนไข/กลุ่มยา; แนบ `evidence_quote`, `source_page`, `pdf_page`, `verified`
- **ไม่ใช้ข้อความเต็มของหนังสือ** (ลิขสิทธิ์ ข้อ 9 และไฟล์ `work/` ไม่ขึ้น git)
- **วิธีค้น:** ความคล้ายแบบ Dice บน n-gram ตัวอักษร (bigram+trigram) เพราะภาษาไทยไม่มีช่องว่างคั่นคำ ใช้ stdlib ผลซ้ำได้เสมอ ไม่มี dependency และ boost รายการของสมุนไพรที่อยู่ในผลตรวจ
- **เกณฑ์/น้ำหนัก** (`rag_min_score`, `rag_top_k`, boost) อยู่ใน `data/config.json` ปรับตามชุดทดสอบ
- **ข้อจำกัดที่ยอมรับ:** n-gram จับความหมายเชิงเหตุผลได้จำกัด (การตัดสินใจเลือกวิธีง่ายและตรวจซ้ำได้ แลกกับความแม่นเชิงความหมาย) วัดด้วยชุดทดสอบและรายงานตามจริง

## 6. Intent และข้อความตายตัว (ทั้งหมดเป็นค่าที่ทีมตั้ง อยู่ใน config ติดป้าย "ร่าง ผู้เชี่ยวชาญต้องตรวจ")
| intent | ตัวจับ (คำสำคัญ) | ผล |
|---|---|---|
| emergency | หายใจลำบาก/หอบ แพ้รุนแรง/บวมหน้า-ปาก-คอ เลือดออกมาก ชัก หมดสติ ฯลฯ (ชุดเล็ก ให้ทีมตรวจ) | แจ้งให้ไปพบแพทย์/ห้องฉุกเฉินหรือโทร 1669 ทันที ไม่ค้น ไม่เรียก LLM |
| safety_yesno | "ปลอดภัยไหม" "กินได้ไหม" "ใช้ได้ไหม" ฯลฯ | ไม่ตอบใช่/ไม่ใช่ แสดงธงที่พบ หรือ "ไม่พบธงเตือนในฐานข้อมูลนี้ ไม่ได้แปลว่าปลอดภัย" + ปรึกษาเภสัชกร |
| dose | "กี่เม็ด" "ขนาด" "วันละกี่" ฯลฯ | ปฏิเสธ ไม่ให้ขนาดยา ชี้ให้ปรึกษาเภสัชกร |
| diagnosis | "เป็นโรคอะไร" "วินิจฉัย" ฯลฯ | ปฏิเสธ ไม่ใช่เครื่องมือวินิจฉัย |
| lookup | อื่น ๆ | ค้นตามข้อ 5 |

ลำดับความสำคัญ: emergency > safety_yesno/dose/diagnosis > lookup เบอร์ฉุกเฉินและคำเตือนเป็นข้อมูลที่ทีมต้องยืนยันก่อนใช้จริง (ผมจะไม่เติมจากความจำ)

## 7. การเรียบเรียงด้วย LLM (ตัวเลือก) และตัวตรวจ
- ส่งให้ LLM: คำถาม (ในแท็กข้อมูล) + รายการที่ค้นได้ (รหัส + ข้อความ) เท่านั้น ตอบ JSON `{answer_th, cites:[รหัส]}`
- ตัวตรวจ (ใช้ซ้ำของเดิมใน `engine/llm.py`): schema; `cites` ไม่ว่างและเป็นชุดย่อยของที่ค้นได้; อักขระแปลกปลอม/URL/markup/ความยาว (`_foreign`); คำต้องห้ามจาก config; ตัวเลขและคำอังกฤษทุกคำต้องอยู่ในข้อความที่ค้นได้; ชื่อสมุนไพร/ยานอกรายการที่ค้นได้ = ตก; ตัวตรวจการกลับความหมายแบบหยาบ
- ตก/ไม่มี LLM/มี error -> คำตอบแบบสกัดข้อความ (ผู้ใช้เห็นป้ายที่มา)
- ใช้โซ่โมเดลและการลองใหม่ที่มีอยู่ (`default_complete`)

## 8. สัญญา API
`POST /api/ask` ตัวเข้า: `{herbs, drugs, profile}` (ตรวจเหมือน `/api/analyze`) + `question` (1-300 ตัวอักษร) + `context_herbs` (รายการ id ที่ต้องอยู่ในฐานข้อมูล ≤ 5) ผิดรูป -> 400
ตัวออก: `{answer: {source, text_th, cites: [{item_id, herb_id, herb_name_th, source_page, pdf_page, evidence_quote, verified}], follow_ups: [ข้อความคำถามแนะนำ ≤ 3], rejected_reason}}` ไม่มี LLM ก็ตอบ 200 (แบบสกัด) ไม่ใช่ 503

## 9. หน้าจอ (เฉพาะแผงแชต)
- **ปุ่มแชตลอย** มุมขวาล่าง ชื่อเข้าถึงได้ "เปิดผู้ช่วย AI" ไอคอนใบไม้/หัวใจ ไม่ใช้ภาพหรือชื่อบุคคลที่ชวนเข้าใจว่าเป็นแพทย์
- **แผง** (`role="dialog"` ไม่บล็อกหน้า มีชื่อ) หัวแผง "ผู้ช่วย AI (ต้นแบบ)" แถบคงที่ "ไม่ใช่การวินิจฉัย · ข้อมูลยังเป็นร่าง · ห้ามพิมพ์ข้อมูลส่วนตัว" + ขอบเขต (X จาก 50 ชนิด) บนมือถือเต็มจอ
- **ข้อความ** ในพื้นที่ `role="log"` ฟองของผู้ใช้/ผู้ช่วยแยกชัด ผู้ช่วยมีป้ายที่มา (ข้อความจากฐานข้อมูล / AI เรียบเรียงจากข้อความที่ค้นได้ / ปฏิเสธ / ฉุกเฉิน) และปุ่ม "ดูหลักฐานในหนังสือ" ใช้ส่วนประกอบเดียวกับการ์ดธง
- **ชิปคำถามแนะนำ** กดส่งได้ + ปุ่มบนการ์ดธง "ถามเรื่องธงนี้" ที่เติมคำถามลงช่องให้ผู้ใช้กดส่งเอง
- **ประวัติ:** `sessionStorage` เก็บเฉพาะข้อความถามตอบ (ไม่เก็บโปรไฟล์) ≤ 50 ข้อความ, ปุ่ม "ล้างประวัติ", ล้างเมื่อปิดแท็บ ผูกกับชุดข้อมูลที่ตรวจ (แก้ข้อมูลแล้วขึ้นข้อความ "ผลตรวจเปลี่ยนแล้ว คำตอบก่อนหน้าอาจไม่ตรงกับข้อมูลปัจจุบัน")
- **การเข้าถึง:** เปิดแล้วโฟกัสไปที่ช่องพิมพ์ Esc ปิดแล้วโฟกัสกลับปุ่มแชต ข้อความใหม่ประกาศผ่าน log ปุ่มมีชื่อ ไม่พึ่งสีอย่างเดียว เคารพ reduced-motion ซ่อนตอนพิมพ์
- ถ้า API ล้มเหลว: ข้อความ `role="alert"` ในแผง ไม่ทำให้ประวัติหาย

## 11. การทดสอบและการประเมิน
- **หน่วย:** ค้นถูกรายการ (เช่น "ขิงกับยากันเลือดเป็นลิ่ม" -> `khing.drug_cautions`), การกรองขอบเขตสมุนไพร, intent ทุกชนิด, ปฏิเสธเมื่อคะแนนต่ำ, ทำซ้ำได้ (คำถามเดิมได้ผลเดิม)
- **guardrail:** LLM จำลองตอบแบบประสงค์ร้าย (cites ปลอม, ชื่อยาแต่ง, URL, คำปลอบใจ, ข้อความนอกรายการ) -> ต้องกลับไปแบบสกัดเสมอ
- **ชุดประเมิน** `docs/rag_eval.json` ~20 คำถาม: ระบุรหัสรายการที่ควรค้นเจอ (อ้างอิงจากข้อมูลที่ตรวจวลีกับต้นฉบับแล้ว) + คำถามที่ต้องปฏิเสธ/ฉุกเฉิน รายงาน recall@k และอัตราปฏิเสธถูกต้อง **ตามจริง** (ชุดนี้ผมร่างเอง ผู้ตรวจควรทบทวน)
- **API/UI:** เปิด/ปิด โฟกัส Esc ประวัติคงอยู่ใน sessionStorage และล้างได้ ข้อความฉุกเฉิน การปฏิเสธ ป้ายที่มา ชื่อปุ่ม/ARIA และ mutation check ของจุดสำคัญ
- **ที่ทดสอบไม่ได้:** LLM จริง (ไม่มี key ในเครื่องผม ให้ผู้ใช้ลอง) และโปรแกรมอ่านหน้าจอจริง

## 12. ความเสี่ยง
- การค้นด้วย n-gram อาจพลาดคำถามที่ใช้คำต่างจากข้อมูล -> ปฏิเสธอย่างปลอดภัยแทนการเดา (วัดด้วยชุดประเมิน)
- รายการ intent/ฉุกเฉินเป็นร่างของทีม ไม่ครบ ต้องผู้เชี่ยวชาญตรวจก่อนใช้จริง
- ผู้ใช้อาจพิมพ์ข้อมูลส่วนตัวในแชต -> มีคำเตือน, ไม่เก็บฝั่งเซิร์ฟเวอร์, ล้างประวัติได้; ข้อความคำถามยังถูกส่งไปผู้ให้บริการ LLM เมื่อใช้ตัวเรียบเรียง
- ฟีเจอร์ AI ใช้โควตา API ฟรีของทีม -> ใช้โซ่โมเดลที่มีอยู่ และต้นทางคำตอบหลักไม่พึ่ง LLM
