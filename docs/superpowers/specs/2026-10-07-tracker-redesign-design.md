# สเปก: ดีไซน์เว็บใหม่ + ตัวติดตามสมุนไพร/ยา "ช่วงนี้" (งานย่อยที่ 1 จาก 3)

สถานะ: ร่างรอทีมรีวิว (2026-10-07) · ผู้ตัดสินใจ: ทีม (ตอบคำถามในแชต 2026-10-07)

## 1. เป้าหมาย และสิ่งที่ผู้ใช้ได้
เปลี่ยนเว็บจาก "ฟอร์มตรวจครั้งเดียว" เป็นแอปติดตามแนว herb tracker: ผู้ใช้บันทึกสมุนไพรและยาที่ใช้อยู่ (พร้อมวันที่เริ่ม) ดูประวัติ และเห็นแผง "ช่วงนี้" ที่แบ่งผลตรวจเป็น ควรหลีกเลี่ยง / ควรระวัง / ข้อมูลเพิ่มเติม พร้อมสถานะรายการ "ไม่พบธงเตือนในฐานข้อมูลนี้" และ "ยังไม่มีข้อมูลตรวจ" ทุกธงมีเลขหน้าหนังสือ

ความสำเร็จวัดได้: (1) ทุกสถานการณ์ของเทสต์ jsdom เดิม (scenario 0-23) มีเทสต์ใหม่ที่ตรวจเรื่องเดียวกันและผ่าน (2) pytest, golden, ชุดประเมิน RAG ยังผ่านเท่าเดิม (3) หน้าใหม่ deploy บน Vercel preview ได้ (4) ไม่มีข้อความ UI ที่ละเมิดกฎข้อ 5

## 2. ขอบเขต
**แผนงานย่อยทั้งหมด** (ตกลงกับทีมแล้ว ทำทีละงาน แยก spec/แผน/ทดสอบ):
1. **สเปกนี้:** ดีไซน์ใหม่ + ตัวติดตาม เก็บในเครื่องผู้ใช้เท่านั้น
2. คำแนะนำช่วงนี้ขั้นต่อไป: คำนวณล่วงหน้า (เช่น ใกล้ครบเกณฑ์ระยะเวลา) ต้องเพิ่มพฤติกรรมใหม่ของ engine + เทสต์ + golden
3. บัญชีผู้ใช้ เก็บบนเซิร์ฟเวอร์ ความยินยอมตาม PDPA (ต้องแก้กฎข้อ 10 ใน CLAUDE.md ตามที่ทีมอนุมัติหลักการแล้ว + เลือกผู้ให้บริการฐานข้อมูล + สร้างโปรเจกต์ภายนอก ต้องขออนุมัติทีมก่อนทำ)

**ไม่ทำในสเปกนี้ (YAGNI):** บัญชี/เซิร์ฟเวอร์เก็บข้อมูล, ระบบเตือนเวลากินยา, streak/เกม, ขนาดยา/เวลากิน, "ควรทานอะไร" (ฐานข้อมูลมีแต่ข้อห้าม/ข้อควรระวัง ไม่มีสรรพคุณ), การตรวจย้อนหลังของรายการที่หยุดแล้ว, การเปลี่ยนกฎ/ข้อมูลของ engine

## 3. หลักการที่ห้ามละเมิด (อ้าง CLAUDE.md)
- กฎข้อ 1/3: ทุกคำเตือนมาจากผลของ `check()` เท่านั้น หน้าเว็บไม่จัดกลุ่มหรือตัดสินเอง ใช้ `severity` ที่ engine คืน (`avoid` / `caution` / `info`)
- กฎข้อ 5: ห้ามใช้ "ปลอดภัย/ใช้ได้อย่างเหมาะสม" เป็นข้อสรุป รายการที่ไม่มีธงแสดงเป็น "ไม่พบธงเตือนในฐานข้อมูลนี้" พร้อมขอบเขตความครอบคลุมและข้อความไม่ใช่การวินิจฉัยบนทุกมุมมองผลลัพธ์ สถานะ "ไม่พบธง" ใช้เฉพาะรายการที่ตรวจแล้วจริง สมุนไพรที่ยังไม่อยู่ในฐานข้อมูล (ขณะนี้ 21 จาก 50) หรือยาที่ไม่อยู่ในแผนที่กลุ่มยา แสดง "ยังไม่มีข้อมูลตรวจ" ไม่ปล่อยให้ดูเหมือนไม่มีธง
- กฎข้อ 7: ข้อความและเกณฑ์ที่ทีมตั้งเองมาจาก `data/config.json` / `/api/meta` ไม่ฝังในหน้าเว็บ
- กฎข้อ 10: ข้อมูลในตัวติดตามอยู่ใน localStorage ของผู้ใช้เท่านั้น ไม่ส่งขึ้นเซิร์ฟเวอร์เพื่อเก็บ ไม่ลง log หน้าแสดงคำเตือนห้ามพิมพ์ข้อมูลส่วนบุคคลจริงเกินที่จำเป็น และมีปุ่มลบข้อมูลทั้งหมด
- ห้ามสร้างผลตรวจฝั่งเบราว์เซอร์: ผลทุกอย่างมาจาก `/api/analyze`

## 4. เครื่องมือและโครงสร้าง
- Vite + Preact + TypeScript โค้ดอยู่ `web/` (`web/src/`: components, store, api, i18n/ข้อความคงที่ที่ไม่ใช่ของทีม) `api/*.py`, `engine/`, `data/` ไม่แก้
- ที่เก็บข้อมูลอยู่หลังอินเทอร์เฟซ `TrackerStore` (อ่าน/เขียนรายการและโปรไฟล์) ตอนนี้ใช้ localStorage; งานย่อยที่ 3 สลับ implementation ได้โดยไม่รื้อหน้าจอ
- Vercel: `buildCommand` + `outputDirectory: web/dist`; ฟังก์ชัน Python `api/*.py` คงเดิม; ห้ามมี `requirements.txt` ที่ root (ใช้ `package.json` ฝั่ง Node เท่านั้น) **ยังไม่ยืนยันว่า Vite + Python functions อยู่ร่วมกันได้บน Vercel** ต้องทดสอบบน preview deploy เป็นขั้นหนึ่งของแผน
- Header ความปลอดภัยและ noindex ใน `vercel.json` คงเดิม
- ห้ามใช้ `dangerouslySetInnerHTML` (เทสต์สแกนซอร์ส)

## 5. หน้าจอ
1. **ช่วงนี้ (หน้าแรก):** หัวมีชิปขอบเขต (`/api/meta.coverage`: สมุนไพร X จาก 50 ชนิด, N กลุ่มยา); แถบสรุปจำนวนแต่ละกลุ่ม (กดข้ามไปกลุ่มนั้น); แผงธง 3 กลุ่ม (ควรหลีกเลี่ยงกางไว้ ที่เหลือพับ) การ์ดธงกางดูเหตุผล เลขหน้า ระดับหลักฐาน สถานะ verified และหลักฐานสั้นด้วยคอมโพเนนต์หลักฐานเดิม; รายการ "กำลังใช้อยู่" แต่ละแถวมีชื่อ ชนิด "วันที่ N" สถานะตรวจ และเมนูแก้ไข/หยุดใช้; แถบล่างมีปุ่ม "+ เพิ่ม" กับข้อความไม่ใช่การวินิจฉัย/ปรึกษาเภสัชกร
2. **เพิ่ม (bottom sheet):** ค้นหาสมุนไพร/ยา (รายการจาก `/api/meta`) + วันที่เริ่ม; ตรวจ input ก่อนเพิ่ม (วันที่ไม่ใช่อนาคต ไม่เกิน 365 วันย้อนหลัง); เพิ่มแล้วตรวจใหม่ทันที (ที่ทำจริง: แผงเพิ่มเป็น dialog แบบ inline ไม่ modal แสดงใต้แผง ไม่ใช่ bottom sheet ติดขอบล่างและไม่มี focus trap แบบเดียวกับแผงแชต รอทีมตัดสินว่าจะเปลี่ยนหรือไม่)
3. **ที่เคยใช้:** รายการที่หยุดแล้วพร้อมช่วงวันที่ ไม่ตรวจย้อนหลัง
4. **ข้อมูลของฉัน:** โปรไฟล์ (อายุ, ตั้งครรภ์ ใช่/ไม่ใช่/ไม่ระบุ, ให้นมบุตร, โรค); ส่งออก/นำเข้า JSON; ลบข้อมูลทั้งหมด; พิมพ์/บันทึกใบสรุปเภสัชกรจาก `/api/analyze` (ผลเดิม)
5. **แชต:** ฟังก์ชันเดิม (ปุ่มลอย ประวัติ sessionStorage ฉุกเฉิน stale note) ย้ายเป็นคอมโพเนนต์ สมุนไพรที่กำลังใช้ส่งเป็น `herbs` (ร่วมกับยาและโปรไฟล์) ส่วน `context_herbs` = รหัสสมุนไพรจาก cites ของคำตอบล่าสุด ไม่เกิน 5 ชนิด เฉพาะที่รู้จัก (ตามหน้าเดิม; แก้ข้อความสเปก 2026-10-08 ให้ตรงกับที่ทำ)

## 6. โมเดลข้อมูล (เก็บเฉพาะที่จำเป็น)
- `item`: `id`, `kind` (`herb`|`drug`), `ref` (รหัสสมุนไพรหรือชื่อยา), `label`, `start_date` (YYYY-MM-DD), `end_date` (ว่างถ้ายังใช้อยู่)
- `profile`: `age` (ว่างได้), `pregnant` (`yes`|`no`|ว่าง), `breastfeeding` (เช่นกัน), `conditions[]`
- ไม่เก็บ: ชื่อจริง อีเมล ผลตรวจ ข้อความแชต (แชตใช้ sessionStorage เดิม ไม่เก็บโปรไฟล์) ผลตรวจคำนวณใหม่ทุกครั้ง

## 7. การไหลของข้อมูลแผง "ช่วงนี้"
```
TrackerStore (items + profile)
   -> สร้าง payload: herbs = [{id, days_in_use = วันนี้ - start_date + 1}] ของรายการที่กำลังใช้,
      drugs = ชื่อยาที่กำลังใช้, profile
   -> (หน่วงเวลาเล็กน้อย) POST /api/analyze    (ต้องมีสมุนไพรอย่างน้อย 1 ชนิดตาม service.validate;
                                                ถ้าไม่มี ไม่เรียก และแสดงว่ายังไม่มีสมุนไพรให้ตรวจ)
   -> จัดกลุ่มธงตาม severity ที่ engine คืน; สถานะต่อรายการ: มีธง | ไม่พบธงเตือนในฐานข้อมูลนี้ | ยังไม่มีข้อมูลตรวจ
      (ใช้ coverage.not_checked / unknown_inputs ของผลตรวจ)
   -> แถบสรุป + แผง; ประกาศผลทาง aria-live
```
ตัวแจ้งเตือนเด่น (แบนเนอร์) มีเฉพาะระดับ `avoid`

## 8. หน้าตา
- สี: ฟ้าคราม + เขียวสุขภาพเป็นพื้นหลัง/ตกแต่ง; สีข้อความและปุ่มใช้เฉดเข้ม (`#0E7490`) ให้คอนทราสต์ ≥ 4.5:1 (เฉด `#0891B2` ที่ skill แนะนำต่ำกว่าเกณฑ์สำหรับข้อความบนพื้นขาว)
- ป้ายความรุนแรงทุกอันใช้ สี + ไอคอน SVG + ข้อความ: ควรหลีกเลี่ยง = แดงเข้ม, ควรระวัง = เหลืองอำพันเข้ม, ข้อมูลเพิ่มเติม = น้ำเงินเข้ม, ไม่พบธงเตือนในฐานข้อมูลนี้ = เทาน้ำเงินเป็นกลาง **ไม่ใช้สีเขียว**, ยังไม่มีข้อมูลตรวจ = กรอบเส้นประ
- ฟอนต์ Noto Sans Thai (400/500/700) ขนาดฐาน 16px ความสูงบรรทัด 1.6; ปุ่ม/ตัวควบคุมสัมผัส ≥ 44px; ธีมมืดตามระบบ; ปิดแอนิเมชันตาม reduced-motion; ไม่ใช้ Neumorphism และอีโมจิเป็นไอคอน
- แผงแชตใช้โทนเดียวกับทั้งเว็บ

## 9. ข้อผิดพลาดที่ต้องรองรับ
- `/api/analyze` ล้มเหลว/หมดเวลา: คงผลล่าสุดพร้อมป้าย "ผลนี้เก่า ตรวจไม่สำเร็จ" + ปุ่มลองใหม่ ไม่ล้างรายการ; ข้อความไม่แสดงรหัสข้อผิดพลาดดิบ
- ผลที่เก่าเมื่อผู้ใช้แก้รายการระหว่างรอ: ไม่แสดงผลเก่าเหมือนปัจจุบัน (ใช้ตัวนับรุ่น เหมือนหน้าเดิม)
- localStorage ใช้ไม่ได้: ทำงานในหน่วยความจำ แจ้ง "ข้อมูลจะหายเมื่อปิดหน้านี้"
- นำเข้า JSON ผิดรูปแบบ/ขนาดเกิน: ปฏิเสธทั้งไฟล์พร้อมเหตุผล ไม่นำเข้าบางส่วน
- ข้อมูลใน localStorage เสียหาย: เริ่มใหม่อย่างปลอดภัยและแจ้งผู้ใช้ ไม่ทำให้หน้าพัง

## 10. การย้ายและเทสต์
- สร้างหน้าใหม่ใน `web/` คู่กับ `public/index.html` เดิม ไม่ลบจนกว่า: (ก) เทสต์ใหม่ครอบคลุมทุกสถานการณ์เดิม (ข) pytest/golden/ชุดประเมิน RAG ผ่าน (ค) deploy preview บน Vercel ใช้ได้ จึงสลับ `vercel.json` ไป `web/dist` และตัดหน้าเก่า
- Vitest + Testing Library + jsdom: ตาราง mapping "scenario เดิม -> เทสต์ใหม่" เป็นส่วนหนึ่งของแผน และเทสต์ใหม่ของตัวติดตาม: คำนวณ `days_in_use`, จัดกลุ่มตาม severity, สถานะ "ยังไม่มีข้อมูลตรวจ" ต่างจาก "ไม่พบธง", ไม่ใช้สีเขียว, ส่งออก/นำเข้า/ลบ, ผลเก่า, localStorage ไม่พร้อมใช้, ไม่เก็บข้อมูลโปรไฟล์ใน sessionStorage ของแชต
- เทสต์สแกนซอร์สหน้าเว็บ: ไม่มี "ปลอดภัย" นอกรูปปฏิเสธที่อนุญาต, ไม่มี `dangerouslySetInnerHTML`
- ผลตรวจ engine ไม่เปลี่ยน: golden/pytest เดิมเป็นเกณฑ์ว่าไม่พัง

## 11. ความเสี่ยง
- ต้องเขียนเทสต์ UI ใหม่ทั้งชุดและย้าย 20+ พฤติกรรมเดิม (แชต ใบสรุป evidence a11y) เป็นงานใหญ่ที่สุดของงานย่อยนี้
- Vite + Python functions บน Vercel ยังไม่ได้ยืนยัน
- ข้อค้างของงานแชต (คำถามที่มีคำหัวข้อแต่ไม่ได้กรอกข้อมูลนั้น เช่น "ขิงให้เด็กกินได้ไหม" ยังตอบ "ไม่พบธงเตือน") ยังไม่แก้ และจะส่งผลถึงแชตในหน้าใหม่ ควรแก้ก่อนหรือพร้อมงานนี้
- ยังทดสอบด้วยเบราว์เซอร์จริงและ screen reader ไม่ได้ (เหมือนงานก่อน) ต้องให้ทีมตรวจเอง

## 12. สิ่งที่ต้องให้ทีม/ผู้เชี่ยวชาญตัดสิน
- ชื่อกลุ่มและข้อความตายตัวบนหน้าใหม่ (ควรหลีกเลี่ยง / ควรระวัง / ข้อมูลเพิ่มเติม / ยังไม่มีข้อมูลตรวจ / คำเตือนความเป็นส่วนตัว)
- เกณฑ์ว่าธงใดควรเป็นแบนเนอร์เด่น (ขณะนี้เฉพาะ `avoid`)
